# 沙箱方案与威胁模型 — L1 策略沙箱设计与 L2 容器沙箱迁移路径

> 2026-09 · 参考项目：[axocoatl](https://github.com/axocoatl/axocoatl)（Rust，Apache-2.0，local-first coding agent 工作台）
> 本文回答三个问题：axocoatl 的沙箱怎么做的、我们为什么先做 L1 策略沙箱、将来要上 L2 容器沙箱时路怎么走。

---

## 1. 背景

本项目所有 agent 能力（飞书对话、E2E 群聊、供应商工作台、数字员工）都跑在**常驻 Claude CLI 子进程**上，
此前统一使用 `--permission-mode bypassPermissions`（全权限）——起因是无头(-p)模式下没有交互界面，
acceptEdits 只放行文件编辑，git/curl 等命令会弹审批 → 无人可批 → 任务静默卡死。
全权限解决了"卡死"，代价是 agent 拥有整台机器的能力面。

数字员工上线后（员工自动并行执行需求、还能经权限创建 E2E/Hook/供应商工作），
"某个员工被 prompt injection 说服执行了越权命令"从理论风险变成了值得设防的场景。
用户诉求：**数字员工在沙箱里工作**。

## 2. axocoatl 的沙箱怎么做的（调研摘要）

**拓扑**："agent 在外、工具进容器"。daemon 与 LLM 循环跑宿主机，每个 Session 一个**长驻 rootless Podman
容器**（`sleep infinity`），全部工具调用（文件/bash/后台任务/PTY）翻译成 `podman exec` 进容器执行；
容器只 bind-mount 该 Session 的工作目录（同路径 `{dir}:{dir}:rw`），`$HOME`、SSH key、兄弟项目不可见。

**关键参数**：`--security-opt=no-new-privileges` + drop 11 个 capability（SYS_ADMIN/SYS_PTRACE/SYS_MODULE/
SYS_RAWIO/NET_ADMIN/NET_RAW…）、网络 `bridge|none` 二选一、`--memory 2g --cpus 2 --pids-limit 512`、
镜像白名单（curated images，非白名单需显式 trust，绝不静默替换）、Preview 端口只绑 `127.0.0.1`。

**威胁模型（原文立场，值得全文背诵）**：沙箱的目的是 *"contain the blast radius of a mistaken or
misbehaving agent"*——**防失误/失控，不防恶意**。明确声明不防：prompt injection（"隔离圈住爆炸半径，
防不了 agent 被说服做错事"）、容器逃逸 CVE、工作目录内的破坏（`rm -rf` 仍会毁掉挂载的仓库——接受的代价）。

**工程哲学（本次移植抄了三条）**：
1. **fail-closed**：没装 Podman → 拒绝提供工具并给手工安装指令，绝不静默降级成无沙箱直跑；
2. **抽象后端**：`Sandbox` trait 两个实现（本地 Podman / 远程 E2B microVM），工具层只依赖接口；
3. **诚实文档**：把"不防什么"写进 README，防止使用者产生虚假安全感。

## 3. 为什么我们先做 L1 而不是照搬容器

环境探测（本机 = Windows Server 2022 Datacenter 云桌面）：

| 项 | 状态 | 对 L2 的影响 |
|---|---|---|
| Hypervisor | ✅ 运行中 | WSL2 可用，硬件不设限 |
| WSL2 | ✅ 框架已装、**无发行版** | 需 `wsl --install`（管理员）+ 装 Podman + 构建镜像 |
| Podman/Docker | ❌ 未装 | 全部要从零建 |
| 工作负载 | **Windows 原生**（D:\、Z:\、Windows mvn/IDEA 工具链、cmd/powershell） | **硬伤**：Linux 容器里跑不了 Windows 工具链；跨 OS 挂载（/mnt/d）路径要翻译、9p 小文件性能差 |
| Claude CLI 工具面 | 黑盒（Bash/Read/Edit 在 CLI 进程内执行于宿主） | axocoatl 能"工具进容器"是因为工具是它自己写的；要让 CLI 的工具进容器，要么整个 CLI 进容器（凭据也得挂进去、断网旋钮作废），要么用 MCP 自定义工具整体替换内置工具面（工程量大） |

结论：**L2 容器沙箱在当前环境成本远大于收益**；而 Claude CLI 2.1.267 原生权限系统提供了
零基建、Windows 原生、经实测达到同等"爆炸半径控制"目标的 **L1 策略沙箱**。
架构上按 axocoatl 的形状留好演进位：档位是实例的属性、策略是独立类（`SandboxPolicy`）、
枚举里预留 `LEVEL_CONTAINER = 9`。

## 4. L1 策略沙箱设计（已实现）

### 4.1 三档预设（实例级配置，`bot_instance.sandbox_level`）

| 档 | 名称 | 旗标组合（实测验证） | 语义 |
|---|---|---|---|
| 0 | 🔓 全权限（默认） | `--permission-mode bypassPermissions` | 现状行为，admin 信任实例 |
| 1 | 🛡 宽松策略沙箱 | `--permission-mode acceptEdits` + `--permission-prompts none` + `--allowedTools "<Bash白名单> Read Edit Write Glob Grep Task TodoWrite WebFetch"` | 白名单命令放行、工作目录内编辑自动通过、**其余一律自动拒绝**（不卡死，拒绝记入 result.permission_denials） |
| 2 | 🔒 严格策略沙箱 | `--restricted` + `--tools "Bash,Read,Edit,Write,Glob,Grep,Task,TodoWrite"` + `--permission-prompts none` + `--allowedTools "<同款白名单>"` | 宽松档全部语义 + **文件工具结构性圈禁在工作目录**（跨目录 Read/Write 直接拒绝）+ **忽略仓库 .claude/settings**（防打开恶意仓库被配置提权）+ 摘除 WebFetch/WebSearch + CLI 拒绝 bypassPermissions |

**Bash 白名单**（两档共用，`SandboxPolicy.BASH_ALLOW`）：
`git mvn npm npx node java javac curl python pip ls dir cat type mkdir cp mv grep findstr echo`（各 `Bash(x:*)` 前缀匹配）。
**刻意排除**：`cmd`/`powershell`（纯 shell，放行等于白名单形同虚设）、`rm`/`del`/`taskkill`（破坏性）。

**fail-closed**：未知档位（含未实现的 9）按最严格档拼旗标并告警，绝不静默回退全权限。

### 4.2 实测记录（verify/sandbox，真实 CLI 2.1.267 + qwen3.8-flash-anthropic）

| 探针 | 宽松档 | 严格档 |
|---|---|---|
| `git rev-parse --show-toplevel`（白名单） | ✅ 放行 | ✅ 放行 |
| `cmd /c time /t`（白名单外，时间敏感探针防编造） | ❌ 自动拒绝 + `permission_denials` 完整记录 | ❌ 自动拒绝 |
| 工作目录内 Write→Read→Edit（磁盘验证 probe.txt） | ✅（acceptEdits） | ✅ 经 allowedTools 白名单放行 |
| `Read C:\Windows\win.ini`（跨目录） | 权限行为拒绝 | ❌ **--restricted 结构性拦截** |
| 网关认证（user settings env 块） | ✅ 存活 | ⚠️ **shell 实测"存活"是假象**——测试 shell 环境里已有 ANTHROPIC_* 变量；`--restricted` 忽略 settings 文件意味着 env 块（网关凭证所在处）一并失效，Java 应用进程环境没有这些变量时严格档必然 "Invalid API key · Please run /login"（上线首日实际踩中）。**修复**：`TerminalSession.injectClaudeEnv` 启动 CLI 前把 `~/.claude/settings.json` 的 env 块显式注入子进程环境（putIfAbsent 不覆盖 OS 级配置、凭证不落日志、所有档位统一注入）——restricted 忽略的是 settings 文件，不影响进程环境变量 |
| 流程健康 | result 事件正常、无卡死，模型收到拒绝后自适应并如实报告 DENIED | 同左 |

一个有意思的插曲：早期测试中 `whoami` 看似"绕过"了沙箱——实际是模型没有执行命令，
直接从 system prompt 的 env 信息里**猜到**了用户名（num_turns=2 无工具调用）。
教训：验证沙箱必须用**不可编造的探针**（时间敏感输出 + 磁盘落盘验证 + permission_denials 字段三方印证）。

### 4.3 与数字员工的联动

- **绑定即上锁**：实例被员工绑定 → `sandboxLevel 0→2` 自动开严格档；解绑/删除员工 → `2→0` 自动恢复。
  只动 0↔2：手动设成宽松档(1)的实例是 admin 有意为之，联动不覆盖。
- 档位变更**懒生效**：下次该实例有会话使用时，`ClaudeCodeService.getOrCreate` 检测到 level 变化
  → destroy 重建终端进程（与 workingDir/model 变更同一条既有路径）。
- 配合独占绑定（员工绑定的实例 admin 不能再分配）："**员工的工作机 = 独占 + 严格沙箱**"，
  admin 自己的实例保持全权限——两个世界互不干扰。

### 4.4 威胁模型（诚实声明，学 axocoatl）

**防**：
- 误操作/失控 agent 的越权命令（白名单外一律自动拒绝，且拒绝有审计记录 `permission_denials`）；
- 跨目录文件访问（严格档为 CLI 结构性圈禁，非行为性）；
- 打开恶意仓库被 `.claude/settings` 提权（严格档忽略项目/本地配置文件——供应链防御）；
- 无人值守卡死（`--permission-prompts none` 把"弹审批"变成"自动拒"，流水线继续走，模型可改道）。

**不防（不要有虚假安全感）**：
- **prompt injection 本身**——白名单内的 mvn/node/python 是图灵完备的构建工具/解释器
  （`mvn exec:`、`node -e`、`python -c` 可执行任意代码），被说服的 agent 在白名单内照样能干活。
  这是业务必需能力（对接工作离不开 mvn/node），axocoatl 的容器同样防不了"被说服"，只能圈住爆炸半径；
- 工作目录内的破坏（`git reset --hard`、删业务文件）——与 axocoatl 同款取舍：工作区就是要给它改的；
- 出站网络（白名单含 curl；严格档摘除了 WebFetch 工具但 Bash curl 仍可出网）——真正断网需要 L2 的 `--network none`；
- CLI/网关自身的漏洞。

**配套缓解**（已有或建议）：敏感凭证不进工作目录（axocoatl 原话 "Keep secrets out of the workspace"）、
员工权限最小化（本文档 §4.3 的创建权限闸门）、重要仓库用 git 兜底（改动可 diff/可回滚）。

## 5. L2 容器沙箱迁移路径（预留，未实现）

**触发条件**：出现对抗性场景（处理外部不可信输入/仓库）、或工作负载迁到 Linux、或需要真正断网执行。

**路线**（axocoatl 同款，Windows 上经 WSL2）：
1. 基建：`wsl --install Ubuntu`（管理员）→ WSL 内装 rootless Podman → 构建镜像
   （node + claude CLI + 白名单命令面，参考 axocoatl 的 REQUIRED_COMMANDS probe + distro-aware provisioning）；
2. 抽象：Java 侧建 `SandboxBackend` 接口（`exec/execStdin/spawnBackground/stop`，即 axocoatl `Sandbox` trait
   的裁剪版），`PodmanBackend` 用 ProcessBuilder 调 podman CLI；`SandboxPolicy.LEVEL_CONTAINER(9)` 接入；
3. 容器参数照抄 axocoatl：长驻 `sleep infinity` + 每工具调用 `podman exec`、同路径 bind mount（WSL 内路径）、
   `no-new-privileges` + cap-drop 11 件套、`--network none` 可选、2g/2cpu/512pids、
   `rm --force --time 0 --ignore`、孤儿容器按 label 回收、fail-closed 就绪检查（podman 缺失→拒绝执行并给安装指引）。

**架构分叉点（到时候要拍板）**：
- **(c) CLI 整体进容器**：实现量最小、CLI 内置工具天然被容器边界约束；代价：API 凭据要挂进容器、
  `--network none` 作废（CLI 自己要出网调网关）、Windows 路径 ↔ `/mnt/*` 翻译层；
- **(b) MCP 工具代理**（axocoatl 忠实形态）：CLI 在宿主、deny 内置 Bash/Read/Write/Edit，
  全部工具经自定义 MCP server 代理到 `SandboxBackend.exec`；能保留断网旋钮与凭据隔离，
  但要完整复刻工具面（含路径 confine、输出封顶、位置参数防注入纪律），工程量数倍于 (c)。

**已知障碍清单**（按严重度）：Windows 路径同构性被 podman machine 打破、9p 跨 OS I/O 性能、
rootless cgroup 在 WSL2 常不可用（axocoatl 答案：`require_resource_limits:false` 静默降级）、
podman machine 代理的删除/端口竞态补丁（axocoatl 近半篇幅）、Spring Boot 重启的容器归属
（需要 runtime_authority 等价物：以数据目录哈希打 label + 启动清孤儿）。

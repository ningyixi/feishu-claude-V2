# 从"超时猜测"到"事件驱动"：飞书 × Claude Code 流式方案重构记

> 项目：feishu-claude-V2 —— 把 Claude Code CLI 接入飞书机器人
> 参考实现：[larksuite/openclaw-lark](https://github.com/larksuite/openclaw-lark)（飞书官方出品的 OpenClaw 飞书渠道插件，2.3k+ stars）
> 时间：2026-09

---

## 一、背景：我要解决什么问题

项目的核心链路：

```
飞书用户消息 → WebSocket 长连接 → Java 服务 → 常驻 Claude CLI 子进程
                                                    (stdin/stdout NDJSON 通信)
                飞书卡片回复 ← ────────────────────── ┘
```

两个绕不开的难题：

1. **怎么知道 Claude 什么时候"回答完毕"？** —— CLI 是一个长驻进程，一轮任务里会输出几十上百个事件（思考、工具调用、正文），什么时候算结束？
2. **怎么把过程流式展示给用户？** —— 一轮回答可能持续几分钟，不能让用户干等。

我的第一版答案：**超时 + 防抖猜结束，每秒发新消息模拟流式**。
正确答案（openclaw-lark 的做法）：**协议事件驱动 + 一张卡片原地流式更新**。

下面完整复盘这两条路。

---

## 二、旧方案：用超时"猜"出来的完成判定

### 2.1 设计

Claude CLI 的 `stream-json` 协议里其实有明确的 `result` 事件。但我当时观察到"好像会收到多个 result"（后来证明是误判），于是**不敢信任任何单个事件**，设计了四层防御：

```
收到 result 事件
   │
   ├─ 不立即完成！先 debounce：
   │     无子 Agent → 再等 15 秒
   │     有子 Agent → 再等 90 秒
   │     （期间再来 result 就重置定时器）
   │
   ├─ 空闲超时：stdout 60 秒无输出 → 返回已积累的部分文本
   │
   ├─ 硬上限：单轮 20 分钟 → 强制返回
   │
   └─ 逐行读超时：readLine 120 秒 → 兜底
```

流式输出则是**伪流式**：

```java
// 每秒把缓冲区增量发成一条新的飞书消息
streamFlushTimer = scheduler.scheduleAtFixedRate(() -> {
    if (streamBuffer.length() > 0) {
        String text = streamBuffer.toString();
        streamBuffer.setLength(0);
        followUpCallback.accept(text);   // → 飞书发新消息 "📢 补充回复"
    }
}, 1, 1, TimeUnit.SECONDS);
```

### 2.2 这套方案的实际表现（一堆 bug）

| # | Bug | 根因 |
|---|-----|------|
| 1 | **简单问答也要白等 15 秒**才回复 | result 后强制 debounce，"你好"这种 3 秒能答完的问题要等 18 秒 |
| 2 | **内容重复推送**：同一段话收到两遍 | 1 秒 flush 推送后不更新 `lastSentTextLength`，result 事件到达时又按差值补推一遍；反向时序同样重复 |
| 3 | **长任务被腰斩**：工具跑 2 分钟，60 秒空闲超时把半成品返回了 | 工具执行期间 stdout 可能长时间无事件，空闲超时误判"卡死" |
| 4 | **刷屏**：一轮回答拆成 N 条"📢 补充回复"新消息 | 消息发出即不可撤回，伪流式只能不断发新消息 |
| 5 | **并发消息串写**：连发两条，内容互相污染甚至丢失 | 所有轮次共享 `accumulatedText/streamBuffer`，第二条消息进来直接重置，上一轮未 flush 的内容蒸发 |
| 6 | **失控轮次无法终止**：20 分钟硬上限在流式模式下是 no-op | future 被"立即完成"hack 提前置 done，超时判定形同虚设 |
| 7 | 飞书接口一慢，所有定时器失真 | 1 秒 flush 在**单线程调度器里同步调 HTTP**，阻塞 debounce/idle 全部计时 |
| 8 | readLine 用 `supplyAsync + get(timeout)` 实现超时，超时后旧任务仍阻塞占着 ForkJoinPool，循环又提交新任务 → **两个线程并发读同一个流** | 丢行、交错、commonPool 污染 |

本质问题一句话：**完成判定靠猜，猜就要防，防就要叠超时，超时之间互相打架，每个打架的缝隙里都是一个 bug。**

### 2.3 最要命的是：这些问题"调不好"——参数是零和拉扯

旧方案真正折磨人的地方不是某个 bug，而是**四个超时参数互相耦合，修好一个场景必然弄坏另一个**，怎么调都不收敛：

| 参数 | 调大 → | 调小 → |
|---|---|---|
| debounce 15s / 90s | 简单问答白等更久，用户抱怨"反应慢" | 后续真有输出时提前截断，只回一半 |
| 空闲超时 60s | 进程真卡死后用户要干等更久 | 长工具执行（编译/测试/一次 Bash 跑 2 分钟）被腰斩成半成品 |
| 硬上限 20min | 失控轮次长期占用进程，后续消息全堵死 | 正常大任务被强杀 |
| readLine 120s | — | 与并发读流 bug 纠缠，动不得 |

真实的调参死循环长这样：

```
用户反馈"回复太慢"
  → debounce 15s 调小到 5s
    → 子 Agent 场景提前截断只回一半
      → 给子 Agent 单独调大到 90s
        → hasSubAgents 判定依赖 task_progress 事件时序，偶发误判
          → 普通对话有时也吃 90s 等待，"更慢了"
            → 回调……（无限循环）

用户反馈"长任务返回半成品"
  → 空闲超时 60s 调大到 180s
    → 进程真卡死时用户要等 3 分钟才收到失败提示
      → 调回 60s
        → 腰斩复现……（无限循环）
```

**为什么调不出来？** 因为这些参数不是独立旋钮。方案里没有真正的完成信号，每个参数本质都在猜同一条边界——"Claude 还在干活 vs 已经死了"——而这条边界在不同场景下的真实位置天差地别：

```
场景                 真实的"最后输出→结束"间隔
简单问答             ~0 秒（result 紧随正文）
长思考               思考事件持续流动，无间隔
Bash 跑编译/测试     可能 2-5 分钟无正文输出
子 Agent 编排        task_progress 间歇流动，分钟级
进程真卡死           ∞（永远不会有输出）
```

用"一个静态时间阈值"去逼近"五种分布完全不同的场景"，数学上就不存在最优解——**调参是在给一个错误模型打补丁，补丁之间互相冲突**。而重复推送、并发串写这类 bug 更是结构性的（共享可变状态 + 消息不可撤回），连调参的入口都没有。

最后的心理状态就是：不敢动任何一个数字，动了这里坏那里，方案看起来"能跑"，实际上每个场景都在凑合。

## 三、转折点：研究 openclaw-lark + 实测协议

重构前我做了两件事，这两件事是整个重构的地基。

### 3.1 拆解飞书官方插件 openclaw-lark 的机制

它是飞书开放平台团队给 OpenClaw（个人 AI 助理框架）写的官方渠道插件，做的正是同一件事：agent 流式输出 → 飞书卡片。核心机制：

**① 完成判定 —— 没有任何超时猜测**

```
dispatchReplyFromConfig(...)      ← Promise resolve = agent 本轮真正结束
  → dispatcher.waitForIdle()      ← 排空内部发送队列（最后一次投递可能还在飞）
  → markFullyComplete()           ← 置位门闩标志
  → SDK 触发 onIdle 回调           ← 检查门闩通过，才把卡片切终态
```

`onIdle` 在流式过程中可能被多次触发（每个输出块之间），所以用一个 `dispatchFullyComplete` **门闩**防止中途误收尾——这是它唯一的"防御"，防的是回调时序，而不是猜完成。

**② 卡片流式 —— CardKit 原地更新 + 全量累积文本**

- 一轮对话 = 一张 CardKit 卡片实体（`card.create` 拿 `card_id`，消息里引用它）
- 流式期间调 `cardElement.content()` 更新固定元素，**每次推的是全量累积文本，不是增量**——飞书服务端自己做 diff 并渲染打字机动画，带单调递增 `sequence` 防乱序
- 推全量的妙处：**丢帧自愈**。中间被限频跳过几帧无所谓，下一帧推全量就自动修复
- 结束时 `card.settings(streaming_mode:false)` + `card.update` 整卡替换成终态

**③ 限频对抗 —— 跳帧 + 降级 + 终态兜底，而非重试**

```
节流：CardKit 100ms / im.message.patch 1500ms
mutex + reflush：同一时刻只有一个请求在飞，飞行期间的增量合并成一帧补发
去重：文本没变不发
限频(230020)：直接跳过本帧，下个节流窗口自然带全量重发
降级：CardKit 失败 → 退回 im.message.patch 整卡替换（仍是原地更新）
兜底：中间帧全丢也没事，终态那次完整 card.update 保证最终内容正确
```

思路是"**允许中间过程不完美，保证终局正确**"。

**④ 严格状态机 + 每轮独立对象**

```
idle → creating → streaming → { completed | aborted | terminated | creation_failed }
```

非法转移直接拒绝；进终态后所有回调 no-op；每轮一个独立 controller，天然无并发串写。

### 3.2 实测 Claude CLI 协议（推翻旧假设的关键）

旧方案的 debounce 建立在"子 Agent 场景会产生多个 result"这个假设上。重构前我直接跑真实 CLI 验证：

```bash
claude -p "用 Agent 工具spawn一个子agent回复PONG，然后你回复DONE" \
  --output-format stream-json --verbose --include-partial-messages
```

统计结果：

```
EVENT COUNTS:
  stream_event: 82          ← token 级增量（--include-partial-messages 提供）
  assistant: 4
  system/task_started: 1    ← 子 Agent 活动走独立的 task_* 事件
  system/task_notification: 1
  result/success: 1         ← ★ 即使有子 Agent，每轮也只有一个 result！
```

两个决定性事实：

1. **`result` 事件每轮有且只有一个**（含子 Agent 场景）——它就是协议层的确定性完成信号，携带最终全文、`is_error`、`duration_ms`、`usage`（tokens/缓存）、`total_cost_usd`、模型名。90 秒 debounce 防御的现象根本不存在。
2. **`--include-partial-messages` 能拿到 token 级增量流**：`stream_event` 包裹原始流事件，`content_block_delta` 里有 `text_delta`（正文）和 `thinking_delta`（思考），且带 `parent_tool_use_id` 可区分主/子 Agent。

> 教训：**防御机制不能建在未实测的假设上。** 一次 5 分钟的协议实测，推翻了支撑整个旧方案的根基。

## 四、新方案：事件驱动 + 真流式卡片

### 4.1 完成判定：result = 终局，零等待

```java
// TerminalSession.processEvent —— 唯一的完成路径
case "result" -> handleResult(event);   // 每轮恰好一个，收到即收尾

private void handleResult(JsonObject event) {
    // 最终文本 = result 字段（空白回退累积文本）
    // metrics = duration_ms / usage / total_cost_usd / modelUsage
    turn.future.complete(r);          // 解锁等待线程
    turn.listener.onTurnComplete(r);  // 卡片切终态
}
```

超时**降级为纯兜底**，只在进程真卡死时触发：

- stdout 完全静默 120 秒（thinking/tool 事件都会刷新它，正常工作永远碰不到）→ 判进程卡死，终止 + 自动重启
- 单轮硬上限 30 分钟 → 强制终止 + 自动重启

### 4.2 轮次模型：每轮独立 Turn + 锁串行化

```java
class Turn {                          // 每条用户消息一轮，互不共享
    CompletableFuture<TurnResult> future;
    StringBuilder answerText, thinkingText;
    List<ToolStep> toolSteps;         // tool_use_id → 步骤（名称/状态/耗时）
    TurnListener listener;            // 卡片控制器
}

interface TurnListener {              // 协议事件 → 确定性回调
    void onTurnStart();               // 立即建卡
    void onThinkingDelta(String d);   // 思考增量
    void onTextDelta(String d);       // 正文增量
    void onToolStart(ToolStep s);     // 工具开始（tool_use 块）
    void onToolEnd(ToolStep s);       // 工具结束（tool_result 按 id 匹配）
    void onTurnComplete(TurnResult r);// result 事件，零等待
    void onTurnError(String msg, boolean aborted);
}
```

并发消息用 `ReentrantLock` 串行化：第二条消息先收到 `onQueued()` 提示"排队中"，等上一轮 result 后才写入 stdin——**结构上不可能串写**。

readerLoop 也简化了：单虚拟线程**阻塞 readLine**（删掉 supplyAsync 超时 hack），看门狗独立调度，两者不再互相污染。

### 4.3 流式卡片：CardKit 原地更新（完整复刻 openclaw-lark）

```
onTurnStart
  └→ cardkit.card.create(初始卡: streaming_mode:true
        + 🛠️工具面板占位 + 空 streaming_content 元素)
  └→ im.message.create 引用 {"type":"card","data":{"card_id":...}}

流式期间（reader 线程回调 → 节流 → HTTP 虚拟线程池执行）
  ├→ 正文/思考增量: cardElement.content(element_id=streaming_content,
  │     content=全量累积文本, sequence++)     ← 飞书端 diff + 打字机动画
  ├→ 工具面板: card.update 整卡替换（1500ms 节流，正文一并写入防回退）
  └→ 节流四件套: 300ms 窗口 / mutex+reflush 合并 / lastFlushedText 去重
        / 限频230020 跳帧不重试

onTurnComplete（result 事件，零延迟）
  └→ 等在飞 flush 落地
  └→ card.settings(streaming_mode:false, sequence++)
  └→ card.update(终态卡, sequence++)
        ├ 🛠️ 工具面板折叠：N 步 · 总耗时，每步 成功(绿)/失败(红)
        ├ 💭 思考折叠面板："思考了 X.Xs"
        ├ 正文全量 markdown（超长按段落边界分元素）
        └ footer：已完成 · 耗时 · 模型 / ↑tokens ↓tokens · 缓存命中 · $费用
```

关键工程决策（全部照搬官方插件的验证过的经验）：

| 决策 | 原因 |
|---|---|
| 推**全量累积文本**而非增量 | 丢帧自愈；飞书端 diff 渲染打字机 |
| 限频**跳帧不重试** | 下一帧自带全量，重试反而堆积请求 |
| 终态更新**永远兜底** | 中间帧全丢也能保证用户看到完整结果 |
| HTTP 全部跑在**虚拟线程池** | reader 回调绝不阻塞；定时器只做调度 |
| 状态机终态后**回调 no-op** | 杜绝"结束后还在更新"的竞态 |
| CardKit 失败**自动降级** im.message.patch（1500ms 节流） | 权限没开也能原地更新，不刷屏 |

### 4.4 异常收尾路径（对照 openclaw-lark 的 onError / abortCard / terminated）

| 场景 | 行为 |
|---|---|
| result 带 `is_error` | 终态卡红字"出错" + 错误信息分隔线 |
| 用户发 `/new` | 中止活跃轮次 → 卡片标"已停止" → 销毁重建进程 |
| 进程意外退出 | readerLoop finally 收尾未完成轮次，卡片错误终态 |
| 看门狗判卡死 | 错误收尾 + 自动重启进程，下一条消息无感恢复 |

### 5.1 逐个算账：旧问题是被"解决"还是被"消灭"的

新方案没有去调那四个超时参数，而是**把逼着参数去猜的不确定性整个移除了**：完成有了确定性信号（result 事件）、活跃度有了连续信号（事件流刷新看门狗）、UI 有了有状态载体（卡片实体）。信号到位，拉扯的参数全部退场——所以每个旧问题的结局不是"缓解"，是"这个问题在新架构里无法再发生"：

| 旧问题 | 旧方案里为什么调不好 | 新方案的解法 | 解决性质 |
|---|---|---|---|
| 简单问答白等 15 秒 | debounce 调小 → 子 Agent 截断，两头堵 | `result` 事件到达即收尾，**0 秒等待** | 信号替代猜测：不需要"等一等看还有没有" |
| 长工具执行被 60s 腰斩 | 空闲超时调大 → 卡死恢复变慢，零和 | 工具/思考事件持续刷新看门狗；120s 只兜"**完全静默**"（正常工作永远碰不到） | 结构性："干活中"和"卡死"从此可区分 |
| 内容重复推送 | `lastSentTextLength` 时序补丁越打越复杂 | followUp 补推机制**整体删除**，一张卡片承载全文 | 结构性：问题的载体（多条消息+差值补推）不存在了 |
| 刷屏 N 条"补充回复" | 消息发出不可撤回，无解 | CardKit 卡片**原地更新**，一轮始终一张卡 | 载体升级 |
| 并发消息内容串写 | 共享 buffer，加锁粒度调不对 | 每轮独立 `Turn` 对象 + `turnLock` 串行化 + 排队提示 | 结构性：共享可变状态消失，串写在类型上无法表达 |
| 失控轮次无法终止 | 硬上限与"future 立即完成"hack 互锁，形同虚设 | 看门狗独立于 future 状态：30min 硬上限 → 强制终止 + **自动重启进程** | 职责分离：判定与执行不再互锁 |
| 飞书接口慢拖垮全部定时器 | 单线程调度器里同步调 HTTP，加线程池治标不治本 | HTTP 全走虚拟线程池，定时器只做调度，reader 回调绝不阻塞 | 结构性：IO 与调度分离 |
| readLine 双线程并发读同一 stream | supplyAsync 超时 hack 与 commonPool 纠缠 | 单虚拟线程阻塞 readLine，超时判定交给独立看门狗 | 结构性：hack 整体删除 |
| 卡死后用户干等/收到半成品 | 空闲超时返回"部分文本"，语义暧昧 | 看门狗判卡死 → 明确的错误终态卡 + 自动重启，下一条消息无感恢复 | 语义清晰：失败就是失败，不拿半成品充数 |

一句话总结这次重构的性质：**旧方案的每个 bug 都是"猜测模型"的必然产物，所以修不完；新方案换掉了模型本身，bug 列表随之整体作废。**

## 七、经验总结

1. **先实测协议，再设计防御。** 旧方案的全部复杂度（四层超时）源于一个未验证的假设——"子 Agent 会有多个 result"。5 分钟的实测证明每轮只有一个 result，整个防御体系随之失去存在意义。
2. **完成判定要用协议的确定性信号，超时只能当兜底。** "猜"出来的完成判定，每一层猜测都会引入新的时序 bug。
3. **有状态的 UI 载体（卡片）> 无状态的消息流。** 消息发出去就收不回，任何修正都只能再发一条；卡片实体可以原地更新、可以收尾、可以标记中止。
4. **推全量而非增量，让系统自愈。** 增量协议要求每一帧必达；全量协议只要求最后一帧必达。配合"跳帧不重试 + 终态兜底"，限频从致命问题降级为无感现象。
5. **每轮独立对象 + 状态机，竞态在结构上消失。** 共享可变状态 + 超时重置是竞态温床；独立 Turn + 终态 no-op 让"两轮串写""结束后还在更新"这类 bug 无法表达。
6. **IO 和调度分离。** 定时器线程只做调度，HTTP 全部丢给虚拟线程池——一个慢接口不再拖垮整个判定体系。

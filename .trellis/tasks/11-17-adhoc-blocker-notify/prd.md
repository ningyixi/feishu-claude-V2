# 临时需求「待确认」：停下来并主动通知（对话框 + 飞书）

## 用户诉求（2026-11-17 原话）
「现在不是工作流，但我还是想在执行单个节点的时候，如果遇到卡点的时候能主动发消息跟我说。针对"临时需求"这个功能，直接在对话框和飞书实例发消息告诉我。比如要在配置文件加一个配置、无法确定多酒店查价的时候到底多酒店数量上限是多少，这种待确认的都要问我。」

要点：①不要工作流那套状态机也照样要有卡点；②卡住必须**主动**找人，两个通道（页面对话框 + 飞书实例）；③倾向**多问**，不许猜着改。

## 现状事实（已读码核实）
- **AdHoc 完全没有卡点识别**：`AdHocService` 全文无 `STANDBLOCK`/`pendingQuestion`；`:575` 注释自证"对话轮不走 ACTION_SPEC"。
- **Wiki 段的卡点被吞成成功**：编译 prompt 明确教 agent「无法访问时输出卡点」（`SupplierWikiService.java:139`），但 AdHoc 收下这段文本后照常置 READY → 残缺 Wiki 被当成功产物，后续基于它改代码。这是缺陷。
- **对话轮没有"先问再改"约束**：prompt = `wikiHeaderBlock + 【用户吩咐】 + WORDING_RULE`（`:578-580`），歧义时默认猜着改。
- **推送通道现成**：`FeishuBotService.notifyUser(instanceId, openId, content)`（`:832-839`；实例未连接或 openId 空则**静默跳过**只留 WARN 日志）；严格版 `sendWorkflowNotice(...)`（`:842-`，失败抛异常）。先例 `EmployeeService.java:795`、`E2EOrchestrator.java:822`。收件人 = `bot_instance.authorized_open_id`（任务一 `6f92607` 加了首个私聊者自动绑定后，该列基本不会为空）。
- **续跑无需新机制**：对话轮就在实例主会话里，用户回一句自然续接上下文，不需要 `answerNode`/Flowable/user task。

## 设计决策（已定，实现不必再议）
1. **复用 `【卡点】` 文本协议，不发明新词**：直接借用 `SupplierJobService.STANDBLOCK`（`(?m)^\s*【卡点】`，`:1339`）做判定（引用常量或同正则，别拷一份正则）。全项目一套协议。
2. **对话轮注入"该问就问"纪律**（`buildChatPrompt` 尾部，与 `WORDING_RULE` 并列，作为独立常量便于单测）：需要人拍板的事一律**先输出一行 `【卡点】` + 具体问题，然后本轮不改任何代码/不写任何文件**。清单至少覆盖：要改配置文件或新增配置项、业务参数取值无法确定（例：多酒店查价的酒店数量上限）、影响线上行为或数据、同一需求存在两种以上合理解释、要动的文件不在本次 Wiki 覆盖范围内。纯实现细节（命名、局部写法）不问。**文案本身必须过既有禁词测试**（`SupplierPromptWordingTest` 的剥离式双向断言），别引入"通关/存档/开一局"等被禁说辞。
3. **检测与可见状态**：`ask` 的 TurnListener 拿到终局文本 → 命中卡点 → 该 agent 行 `status=BLOCKED`（保留问题原文），任务行记 `pendingQuestion`（新列，`ddl-auto=update`）。页面顶部一张**常驻「待你确认」卡**（琥珀色、问题原文、输入框就在地下方），不是混在消息流里的一行。用户发下一句即视为答复：清除 `pendingQuestion`、卡片收起、进入进行中。
4. **主动通知双写且失败必须可见**：命中时调 `notifyUser(instanceId, authorizedOpenId, "【临时需求·待确认】<任务名>\n<问题原文>\n\n直接在本对话回复即可，我会继续。")`；`ad_hoc_task` 增 `notified_at` / `notify_error` 两列，把"实例未连接""未绑定 openId"等原因落库，卡片上显示「飞书已通知」或「飞书通知失败：<原因>」。**页面上的待确认卡是权威事实源，飞书只是提醒** —— 绝不允许推送失败后用户毫不知情（`notifyUser` 现在静默 return，实现时要么改为返回布尔/抛错，要么在 AdHoc 侧先自查连接与 openId 再决定文案，二选一并说明取舍）。
5. **Wiki 编译段的卡点不再被吞**：编译返回命中 `【卡点】` → 该段**不得置 READY**，置为待答/FAILED 并把问题原文显示在阶段卡上；用户答复后走现有「重试本段」续跑。

## 验收
- AC1 对话框里吩咐一句注定有歧义的话（例："给多酒店查价加上数量上限"），agent 回输出 `【卡点】` + 具体上限问题，**且本轮不产生任何写操作**；页面出现常驻待确认卡。
- AC2 同一时刻飞书能收到该实例发来的「【临时需求·待确认】…」私聊；把实例 WebSocket 断掉/清空 `authorized_open_id` 时，卡片必须显示「飞书通知失败：<原因>」，不得静默。
- AC3 直接在对话框回一句答复 → 待确认卡消失、`pendingQuestion` 清空、agent 在同一主会话续跑（测试层面断言仍是同一 `TerminalSession`/同 sessionID，且**未新建 lane、未 steer、未打断**）。
- AC4 Wiki 编译输出含 `【卡点】` 时任务不得变 READY，阶段卡显示问题；修掉"残缺 Wiki 被当成功产物"这个缺陷。
- AC5 `notifyUser` 语义变更若影响既有调用方（`EmployeeService`、`E2EOrchestrator`），必须逐处回归，不得改变它们现有的"尽力而为、不阻塞"行为。
- AC6 单测：卡点判定/状态迁移/通知失败落库/prompt 纪律文案（含禁词双向断言）各至少一条；`mvn test` 除 4 条预存 Windows/temp 环境红（`GitPrServiceTest`×2、`WorkspaceGitServiceTest`×1、`SupplierContextTest`×1）外全绿；`npm run build` 通过。

## 明确不做
不改工作台节点状态机、不改 Flowable、不给接口建档（QuickProbe）加通知；不做飞书卡片按钮回调答复（文本回复即可）；不接第三方推送；不做"多人待确认路由"（收件人就是实例绑定的那一个人）。

## 已知局限（必须写进代码注释，别假装没有）
提示词级约束**无法硬拦** agent"先改完再问"。缓解：纪律文案把顺序写死（"输出【卡点】之前不得调用任何写文件/改配置的工具"），并在页面展示本轮工具动作流水，让用户看得见它到底动没动。要真硬保证得引入工具级拦截，超出本任务范围。
